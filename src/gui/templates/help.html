First steps: from empty config to first backup

Dockkeep runs Restic backups and optional Rclone syncs for jobs you define once and then schedule. A fresh installation starts with an empty configuration, so the first backup is roughly six steps.

  1. Create a job. Configuration -> Jobs, then + Create new job. A job groups backups, Rclone tasks, and workflows that belong together and share defaults.
  2. Add a backup. In the job sidebar choose + New backup and fill in the repository, the repository password, and the source paths to back up. Set a schedule if it should run automatically, and retention if old snapshots should be pruned.
  3. Optional: add Rclone tasks and workflows. + New Rclone task copies or syncs data to a remote, + New workflow chains several steps into one run.
  4. Check the result. Effective config in the job sidebar shows the values that will actually be used, including everything inherited from job and global level.
  5. Try it. On the Dashboard, use Dry Run on the new backup first - it exercises the whole path without writing a snapshot. If that looks right, use Start.
  6. Watch it. The Runs panel on the Dashboard and the Runs page show the run; Diagnostics -> Logs shows its output line by line. After the first successful backup, the Repositories page starts showing snapshots.

Creating and editing the configuration

Everything lives in a single config.toml. The structured editor writes it for you and keeps your comments, blank lines, and formatting intact outside the values you actually change.

Global settings

Collapsible section on Configuration -> Jobs. Holds defaults for all jobs, log level and log retention, and the notification providers.

Job pages

The job sidebar has Job settings, Backup defaults, Rclone defaults, and one page per backup, Rclone task, and workflow, plus Effective config.

Raw config

The Raw config button opens the TOML file itself - useful for bulk edits and for anything the structured forms do not cover. It validates before saving.

Rclone remotes

Configuration -> Rclone remotes creates, edits, tests, and deletes remotes in rclone.conf, with a raw editor for remote types the form does not cover.

Names
Jobs, backups, Rclone tasks, and workflows may contain letters, digits, hyphens, and underscores - no dots, spaces, or other characters, because dots separate the parts of a target name. new cannot be used as a name in the editor, and _system is reserved as a job name because it is the system log directory.
Repository credentials
Set exactly one of password, password environment variable, or password file - per level they are mutually exclusive. A password file must be an absolute path that exists when the configuration is loaded.
Schedules
A schedule is a cron expression with exactly five fields (minute hour day month weekday), so 0 2 * * * is daily at 02:00 and */30 * * * * every 30 minutes. The field previews the next runs while you type. All schedules and every next-run time in the UI use the container's local time - check it if runs happen an hour off. Without a schedule a task runs only when you start it.
Workflows
Built from steps you pick as type, target, and action. Backup plan runs the backup with its configured retention and cleanup options; the forced actions run only that single step. The first failing step aborts the workflow.
Saved changes take effect on their own
The scheduler notices a changed configuration and picks it up on its next check, so schedules do not need a restart. If a saved configuration is invalid, the last valid one stays active and the error remains visible until a valid save replaces it.

How settings inherit

Most settings exist on three levels and fall through from top to bottom: global -> job -> backup, workflow, or Rclone task. This is why a backup page can look almost empty and still do the right thing - and why Effective config in the job sidebar is the page to check when a value surprises you: it shows the resolved result after inheritance.

Not set
Inherits the value from the level above. This is the normal case and what an empty field means.
Explicit value
Overrides the inherited value for this level and everything below it.
Explicit off
A switch set to false stops inheritance - it does not fall back to an enabled parent value.
Extra arguments
An empty list is not the same as unset: it stops inheritance and passes no extra arguments at all.
Timeouts and retention
Backup, Rclone, and hook timeouts as well as the Restic keep rules inherit the same way. No effective timeout means the command may run without a time limit.
Not inherited
Lock retry settings, the report schedule, and the per-provider event list exist only globally. The schedule of an Rclone task is set on the task itself and is never inherited from the job.

Retention needs at least one effective keep rule as soon as it is switched on or a workflow runs a retention step - otherwise the configuration is rejected. A backup without any source paths is allowed but reported as a warning.

Rclone tasks: copy and sync

An Rclone task moves a local directory to a remote - typically the Restic repository itself, so a copy of the backup lives off-site. The remote must exist in rclone.conf; create and test it under Configuration -> Rclone remotes. A task pointing at an unknown remote fails immediately.

Copy (default)
With Delete during sync off, Dockkeep runs rclone copy: new and changed files are uploaded, nothing on the target is ever deleted. Files removed locally stay on the remote.
Sync
With Delete during sync on, Dockkeep runs rclone sync and the target mirrors the source - including deletions. Use it only when the remote is meant to be a mirror, not an archive.
Deletion guard
A deleting sync refuses to start when the local source is missing, not a directory, empty, or unreadable; the run fails and names the source in the log instead of clearing the remote. An unmounted volume therefore cannot wipe the target.
Own schedule
An Rclone task is scheduled on the task page itself. Everything else (bandwidth limit, transfers, checkers, extra arguments, timeouts, notifications) inherits from job and global level as usual.

To upload a repository right after the backup that filled it, put both into a workflow instead of giving them two schedules - it keeps the order and stops at the first failing step.

Running jobs and reading run status

Every backup, Rclone task, workflow, and restore becomes a run. Start one manually with Start or Dry Run on the Dashboard, or let the scheduler start it. The Dashboard Runs panel shows active, upcoming, and recent runs; the Runs page adds the full history with filters for job, task, status, and source, plus Details, Logs, and Cancel.

A dry run exercises the whole path but tells Restic and Rclone not to change anything. Configured hooks are skipped in a dry run; a missing repository may still be initialised if auto-init is on.

What the statuses mean

Queued
Accepted and about to start. Cancelling here ends the run before any command is executed.
Running
A command is being executed. Cancelling stops it and its child processes.
Success
All steps finished successfully.
Failed
A step failed. For workflows, the run stopped at the first failing step.
Skipped
A scheduled run could not get its resource lock because the same repository or Rclone endpoint was busy. The run was not started; the next schedule applies as usual.
Lock error
Same cause as skipped, but for a run you started manually - so it is reported as an error rather than silently passed over.
Cancelled
Cancelled from the UI. No further steps, no error hooks, and no notification follow.
Config error
The configuration could not be loaded or is invalid for this target.
Unexpected error
An error outside the normal failure paths. The full stack trace is in the log.

Why runs wait for each other

Runs lock the resources they touch - the Restic repository, the Rclone source and target - so the same repository is never written by two runs at once. A workflow holds the resources of all its steps for its entire runtime.

A lock is never waited on indefinitely: a conflict ends the run immediately as skipped or lock error, unless the global lock retry settings allow a few more attempts.

Starting the same target manually while it is already running does not create a second run - you get the running one back.

After the last step, a run stays in Running for a moment while snapshot and size data are read from the repository. During this phase it can no longer be cancelled. Notifications are sent afterwards.

The scheduler

Scheduled runs need an active scheduler; in this container it belongs to the web UI process. It checks once a minute which schedule is due, uses the container's local time, and picks up a saved configuration change on its next check.

If the Runs page shows that scheduler runs are unavailable, no scheduler is reachable and the page lists manual runs only. The usual cause is a missing or invalid configuration: the UI then starts in recovery mode and the scheduler stays inactive until a valid configuration is saved.

Restoring data

  1. Open Repositories and pick the location you want to restore from, then Snapshots.
  2. Choose the snapshot and open its Restore page.
  3. Pick a mode. Whole snapshot restores everything and optionally narrows the result with either include patterns or exclude patterns - the two cannot be combined. Select files and folders browses the snapshot contents and restores exactly what you tick, without mounting the repository.
  4. Optionally set a target directory and decide whether existing files may be overwritten.
  5. Use Run dry-run first: it reports what would be restored without writing anything. Then Start restore.
  6. The restore shows its progress on the page and appears on the Runs page like any other run. It can be cancelled while it is still running.

Without a target, files land in /restore/<job>/<backup>/<YYYY-MM-DD_HH-MM-SS>_<snapshot>_<suffix>, so a second restore of the same snapshot never overwrites the first. Restores are always confined to the restore base directory /restore; a target outside it is rejected, and so are symlinked path components inside it.

If no configured backup holds credentials for that location any more - for example after the backup was removed from the configuration - the restore page asks for ad-hoc credentials. They are used for this one request only and are never written to the configuration or stored anywhere.

Repositories, snapshots, and refresh

The Repositories page groups by the physical Restic repository, not by configuration: several backups pointing at the same repository appear as one card with one row per storage location. Each row shows the configuration currently pointing at it, or Inactive if none does.

Snapshot lists, sizes, and the growth chart come from Dockkeep's own cache, which is filled while jobs run: a successful backup records the new snapshot and repository size, a retention step reconciles the full snapshot list, a cleanup step records the size again. That is why the page stays fast and works without contacting the repository.

Use Refresh when the repository changed outside Dockkeep - the button on the page refreshes every configured backup, the one on a location refreshes just that location. Locations that no longer have an active configuration can be merged into another location (when a repository moved) or deleted from the overview; this only touches the cache, never the repository or config.toml.

Logs and diagnostics

Diagnostics -> Logs shows one job and one day at a time. Level buttons, the task filter, and the search box narrow down what is displayed. The _system entry in the job list holds everything that does not belong to a job run - scheduler, configuration loading, the web UI itself.

The static view is a snapshot of the moment you opened it. To follow a running job, use Live; it streams new lines until you press Stop.

Log lines follow a fixed format - the date is already in the file name, so the line starts with the time: 

14:03:12 [INFO] [nas] [backup.local] Starting backup
14:03:12 [INFO] [restic] [workflow.nightly › backup.local] Running restic backup

The second tag says who wrote the line: the job name for the run itself, the component for output coming from Restic, Rclone, or a hook. The last tag is the task the line belongs to, which is what the task filter matches - steps inside a workflow are shown nested. Lines without a timestamp, such as stack traces, belong to the line above and are filtered with it.

Diagnostics -> Database is a read-only view of Dockkeep's own SQLite database (run history, restore records, repository artifacts, statistics). It exists for checking what was recorded; it cannot change anything and takes no free-form SQL.

Notifications and reports

Providers are configured in the global section of Configuration -> Jobs and are active as soon as their section exists and is valid - there is no separate enable switch. Test provider sends a single test notification, Test report sends a synthetic periodic report.

Which events a task triggers comes from its notify-on-success, notify-on-error, and notify-on-skipped settings, inherited global -> job -> task. The optional event list per provider only narrows that down; it can never produce an event the task does not trigger. Notify-on-error covers every failing status, cancelled runs never notify.

An optional global report schedule sends a periodic summary of finished runs. It is evaluated by the scheduler, and the summary covers the last complete interval; empty windows are still sent as a heartbeat so a silent channel is recognisable as a problem.

Hooks

Pre, post, and on-error hooks can run around a job and around a single backup or workflow - for example to stop a container before the backup and start it afterwards. Both levels are independent: if a backup fails, first its own on-error hooks run, then the job's.

Failure handling
A failing pre or on-error hook aborts the run. A failing post hook only logs a warning and leaves the result successful.
Script hooks
Must be absolute paths inside /scripts and run directly from there, so the script has to be executable. Arguments after the path are passed through without a shell.
Inline commands
Shell one-liners instead of a script file. They run only if DK_ALLOW_INLINE_HOOKS=true is set on the container.
Dry runs
Configured hooks are not executed in a dry run.

Running Restic and Rclone commands by hand

Some maintenance has no button in the UI - checking a repository, unlocking it after a crash, comparing a remote. For that, open a shell in the container and let dk shell prepare the environment for a configured target; then use restic and rclone natively.

Open a shell

docker exec -it <container-name> bash
docker compose exec <service-name> bash

<container-name> comes from docker ps, <service-name> from your Compose file.

Prepared Restic shell

dk shell <job>.backup.<backup>
restic snapshots
restic check
restic unlock

Sets RESTIC_REPOSITORY and, depending on the configuration, RESTIC_PASSWORD or RESTIC_PASSWORD_FILE.

Prepared Rclone shell

dk shell <job>.rclone.<task>
rclone ls <target>
rclone check <source> <target>

Shows the configured source and target. The active rclone.conf is the one from RCLONE_CONFIG, normally /config/rclone.conf.

Find targets and check the config

dk shell
dk shell <job>
dk config validate

Without a complete target, dk shell lists what is available. dk config validate checks the configuration file without changing anything and also works while the UI is in recovery mode.

Only these two commands work here. This container runs in UI mode, where the web UI is the place to start, schedule, and inspect runs - so dk shell and dk config validate are available and all other dk commands refuse to run and point back to the UI.

Target names

A target names one configured thing. You need this notation for dk shell and when editing the raw TOML; the structured workflow editor picks type, target, and action from dropdowns instead. 

<job>.backup.<backup>
<job>.backup.<backup>.backup
<job>.backup.<backup>.retention
<job>.backup.<backup>.cleanup
<job>.rclone.<task>
<job>.workflow.<workflow>

The three suffixed forms address a single step of a backup instead of the whole plan: only the snapshot, only retention, or only cleanup.

Paths and environment settings

These are the container paths in their default layout. If you changed the corresponding environment variable, the path changes with it.

Config
/config/config.toml; directory override DK_CONFIG_DIR
Rclone config
/config/rclone.conf; override RCLONE_CONFIG
Backups
/backups is the directory the container prepares for local Restic repositories - a repository path is whatever you configure, this is only the intended mount point; override DK_BACKUP_DIR
Logs
Job logs /logs/<job>/<YYYY-MM-DD>.log, system logs /logs/_system/<YYYY-MM-DD>.log; override DK_LOG_DIR
AppData
/appdata holds appdata.db with run history, restore records, repository data, and statistics; override DK_APPDATA_DIR
Restore
/restore; restores only ever write below this directory; override DK_RESTORE_DIR
Hook scripts
/scripts is the working directory for hooks and the only allowed location for script hooks; override DK_SCRIPTS_DIR
Locks
/var/lock for resource locks and the scheduler lock; override DK_LOCK_DIR

Settings that exist only as environment variables

These have no field in the UI on purpose - they belong to the container, not to the configuration file.

DK_APPDATA_RETENTION_DAYS
DK_APPDATA_RETENTION_COUNT
Maximum age in days and maximum number of entries kept in appdata.db. If neither is set, nothing is ever deleted automatically and the database keeps growing - set at least one on a long-running installation. Active runs and data still in use are never removed.
DK_ALLOW_INLINE_HOOKS
Set to true to allow inline shell commands as hooks; otherwise only script files inside /scripts run.
DK_STATS_TIMEOUT
DK_BROWSE_TIMEOUT
Time limit for reading repository statistics after a run (default 600 s) and for listing snapshot contents in the restore browser (default 30 s). Raise them for very large or slow repositories - a timeout names the variable in the log.
DK_NOTIFICATION_TIMEOUT
Time limit for sending one notification (default 10 s).
DK_SIGTERM_GRACE_PERIOD
Seconds a cancelled or timed-out command may shut down cleanly before it is killed (default 10 s).

Recovery mode: if the configuration is missing or invalid, the UI still starts so you can fix it. The scheduler stays inactive until a valid configuration is saved.

The UI has no login. Do not expose it to an untrusted network.
